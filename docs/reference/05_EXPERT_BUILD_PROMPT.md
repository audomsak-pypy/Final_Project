## บทบาทและงานที่ต้องทำ

คุณรับผิดชอบงานในมุมมองของ Business Analyst, Data Analyst, Data Engineer, ผู้พัฒนาเว็บ Python, ผู้ออกแบบ UX/UI และผู้ทดสอบระบบ ให้ทำงานตั้งแต่ตรวจ repository จัดทำ BRD เตรียมข้อมูล พัฒนา Dashboard ทดสอบ แก้ข้อผิดพลาด และส่งมอบโครงการที่รันได้จริง

สร้างเว็บไซต์ภาษาไทยชื่อ **“Adidur — จริงหรือเฟค”** สำหรับรายวิชา **Basic Programming for Data Scientist and Data Visualization** ภายใต้หัวข้อ **“AI ข่าวปลอม และภัยออนไลน์: มองโลก เปรียบเทียบไทย”** ตามเอกสารและภาพแนบ

งานนี้เป็นคำสั่งให้ลงมือพัฒนา ห้ามจบเพียงข้อเสนอ แผนงาน BRD ภาพจำลอง หรือโครงหน้าเว็บที่ใช้ข้อมูลตัวอย่าง ให้สร้าง BRD ที่นำไปพัฒนาต่อได้ แล้วทำงานต่อจนเสร็จภายในขอบเขตที่เข้าถึงได้ ไม่ต้องหยุดรออนุมัติทางเลือกทั่วไปที่ตัดสินใจได้จากข้อกำหนด

ให้รายงานความคืบหน้าสั้น ๆ เมื่อจบแต่ละช่วง โดยระบุสิ่งที่ทำจริง ข้อค้นพบ และอุปสรรคที่มีผลต่อการส่งมอบ หากติดขัด ให้ทำส่วนที่ไม่ขึ้นกับอุปสรรคนั้นต่อ พร้อมแจ้งสิ่งที่ต้องการอย่างเจาะจง

## 3. กรอบคำถามวิจัยที่ BRD และเว็บต้องใช้

รักษาความสนใจเดิมของผู้ใช้ทั้ง 3 เรื่อง แต่แยกสมมติฐานออกจากข้อค้นพบ:

| เรื่อง | คำถามที่ต้องตอบด้วย Dashboard | ข้อจำกัดที่ต้องรักษา |
|---|---|---|
| 1. AI ข่าวเท็จ และการหลอกลวงในไทย | เหตุการณ์ Deepfake ที่ AIID บันทึกกับข่าวเกี่ยวกับ AI ที่ AFNC ตรวจสอบเปลี่ยนแปลงอย่างไร และช่วงเดียวกัน ACSC รายงานคดีกับความเสียหายอย่างไร | ข้อมูลนี้ยังยืนยันไม่ได้ว่าไทยตามหลังโลก 2 ปี หรือ AI ทำให้คดีเพิ่ม |
| 2. ประเด็นต่างประเทศกับไทย | ประเด็นใดปรากฏร่วมกัน และสัดส่วนต่างกันอย่างไรระหว่าง EUvsDisinfo กับ AFNC | ไม่มีคีย์เชื่อมข่าวต่อข่าว จึงยังสรุปการนำเข้าหรือการแพร่ข้ามประเทศไม่ได้ |
| 3. เสรีภาพอินเทอร์เน็ต | ไทยมีคะแนนเท่าไรเมื่อเทียบประเทศในปีเดียวกัน และช่วงเดียวกัน AFNC เผยแพร่ผลตรวจข่าวเท่าไร | จำนวนข่าวที่ถูกตรวจไม่ใช่อัตราการแพร่ข่าวปลอมของประชากร และไม่มีข้อมูลผลลัพธ์แบบเดียวกันครบทุกประเทศ |

ข้อกำหนดเพิ่มเติม:

- “ไทยตามหลังโลกประมาณ 2 ปี”, “ข่าว 11 เป็น 47 เรื่อง”, “คนไทยเลือกนำเข้าข่าวที่กระทบปากท้อง” และ “ประเทศที่ปิดกั้นมีข่าวปลอมน้อยกว่า” เป็นข้อความตั้งต้นที่ต้องตรวจสอบ ห้ามใส่เป็นข้อสรุปสำเร็จรูป
- เอกสาร 02–03 ระบุข่าวเกี่ยวกับ AI 56 โพสต์ รวมปี 2568 จำนวน 11 และปี 2569 จำนวน 44 ต่างจาก 47 ในโจทย์เดิม ให้คำนวณซ้ำและรายงานความต่าง
- อย่าเทียบปี 2568 เต็มปีกับปี 2569 ที่ยังไม่เต็มปีแล้วเรียกเป็นการเติบโตเทียบช่วงเดียวกัน หากเทียบ ม.ค.–ต.ค. ต้องคำนวณทั้งสองปีด้วยช่วงเดียวกัน
- หากข้อมูลรองรับเพียงการพรรณนา ให้เขียนว่า “ยังตอบไม่ได้จากชุดข้อมูลนี้” พร้อมระบุข้อมูลเพิ่มที่จำเป็น เช่น วันเริ่มแพร่จริง การเชื่อมเหตุการณ์ข้ามแหล่ง หรือข้อมูลหลายประเทศที่มีนิยามเดียวกัน
- ไม่ต้องคำนวณสหสัมพันธ์หรือ Time Lag เพื่อให้ดูเป็นงานเชิงสถิติ หากหน่วย ช่วงเวลา การคัดเลือก และการรายงานของข้อมูลยังเปรียบเทียบกันไม่ได้

## 4. จัดทำ BRD จริงก่อนพัฒนา แล้วทำงานต่อ

สร้าง `docs/BRD.md` ภาษาไทย โดยมีเนื้อหาจำเพาะกับโครงการนี้อย่างน้อย:

1. ชื่อโครงการ รุ่นเอกสาร ปัญหา และที่มา โดยไม่เขียนสมมติฐานเป็นข้อเท็จจริง
2. วัตถุประสงค์ทางธุรกิจ/การเรียนรู้ และตัวชี้วัดความสำเร็จที่ตรวจได้
3. ผู้ใช้เป้าหมาย ได้แก่ ผู้เรียน ผู้ประเมิน และประชาชนทั่วไป พร้อมสิ่งที่แต่ละกลุ่มต้องทำได้ ไม่แต่งชื่อผู้รับผิดชอบ
4. ขอบเขตที่ทำและไม่ทำ รวมข้อจำกัดเรื่องการพิสูจน์สาเหตุ การเชื่อมข่าว และการเป็นตัวแทนของประชากร
5. คำถามหลักทั้ง 3 กลุ่ม พร้อมตารางว่าแต่ละข้อใช้ข้อมูลใด ตอบได้ระดับไหน และต้องมีข้อจำกัดอะไร
6. Business Requirements, Functional Requirements และ Non-functional Requirements มีรหัส `BR-xx`, `FR-xx`, `NFR-xx` ลำดับความสำคัญ และเกณฑ์ตรวจรับ
7. Data Requirements: แหล่งข้อมูล ความหมายหนึ่งแถว คีย์ ช่วงเวลา หน่วย การขาดหาย วันตัดข้อมูล และกติกาเตรียมข้อมูล
8. สูตร KPI และตัวหาร แยก “เหตุการณ์ / โพสต์ / การหักล้าง / บทความ / คดี / บาท / คะแนน” ให้ชัด
9. โครงสร้างหน้า User Flow และตารางการเชื่อมตัวกรองกับกราฟ รวม Drill down/up
10. ข้อกำหนดด้านการอ่านภาษาไทย หน้าจอสัมผัส การเข้าถึง ประสิทธิภาพ ดาวน์โหลด และการรันซ้ำ
11. สมมติฐาน ข้อจำกัด ความเสี่ยง และแนวทางรับมือที่เกิดจากข้อมูลจริง
12. เกณฑ์ตรวจรับแบบ Given–When–Then และ Definition of Done

สร้าง `docs/REQUIREMENTS_TRACEABILITY.md` เป็นตาราง:

`รหัสข้อกำหนด → คำถามหลัก → ชุดข้อมูล/หน่วย → รหัส K/C/T/S/D ในเอกสาร 01 → สูตร/คิวรี → ตัวกรองที่มีผล → ไฟล์หรือฟังก์ชัน → test case → ผลทดสอบ`

BRD ต้องครอบคลุมทุกองค์ประกอบในเอกสาร 01 และ 04 รวมแท็บ 4 ส่วนอธิบาย และปุ่มดาวน์โหลด เมื่อแก้การออกแบบภายหลัง ให้อัปเดต BRD และตารางนี้ให้ตรงกับแอปที่ส่งมอบ

## 5. การเตรียมข้อมูลและฐานข้อมูล

- ใช้ Python/Pandas สร้าง SQLite ตามแบบในเอกสาร 03 พร้อม primary key, foreign key ที่ใช้ได้จริง และ index ที่เหมาะกับการกรอง
- ทำ pipeline ให้รันซ้ำได้ด้วยคำสั่งเดียว ไม่พึ่ง path บนเครื่องผู้ใช้ ไม่แก้ข้อมูลต้นฉบับ และไม่ต้องเตรียมข้อมูลด้วยมือก่อนเปิดเว็บ
- สร้าง manifest ระบุชื่อไฟล์ SHA-256, sheet, schema, จำนวนแถวก่อน/หลัง, แถวซ้ำ, ค่าว่าง, ช่วงวันที่ และกฎที่ใช้ เพื่อรู้ว่าค่าทดสอบมาจาก snapshot ใด
- AIID อ่านชีต `Incidents` ด้วย `header=2` นับ `Incident ID` ไม่ซ้ำ ไม่รวม weekly_versions เป็นเหตุการณ์ใหม่
- FOTN ใช้ `(iso3, data_year)` แยก `report_edition`; ตรวจว่าคะแนนรวมเท่ากับผลรวม 3 องค์ประกอบ คะแนนสูงหมายถึงเสรีมาก
- EUvsDisinfo แปลง `debunk_date` ด้วย `%d-%m-%Y` แยกตารางการหักล้างกับบทความและ keywords ป้องกันการนับเพิ่มเมื่อแตกหลายค่า
- AFNC รักษา `post_id` เป็นคีย์ หัวข้อซ้ำแต่คนละ post_id ไม่ใช่เหตุผลให้ลบทิ้ง อ่านชีตจาก Excel ได้เมื่อ CSV ไม่มี
- ตรวจว่าเนื้อหาถูกตัด 500 ตัวอักษรจริงหรือไม่ หากใช่ ให้ระบุว่าการค้น AI เป็นค่าขั้นต่ำและยังต้องตรวจคำชี้แจงต้นทาง ถ้าได้ CSV เต็มให้รองรับการประมวลผลใหม่ และรายงานว่าจำนวนเปลี่ยนอย่างไร
- ACSC รักษาค่าไม่มีรายงานเป็น `NULL` ห้ามเติมศูนย์ ใช้ `weekly_panel` เป็นปฏิทินแสดงช่องว่าง ตรวจให้ยอดรวมตรงกับตารางสัปดาห์ต้นทาง
- แยก `flag_type='suspect'` ออกจาก `note`; สวิตช์รวม/ไม่รวมกระทบเฉพาะ suspect และแสดงผลต่างของยอดรวม
- สัปดาห์ 30 พ.ค.–6 มิ.ย. 2569 มี 8 วันและใน panel จัดไว้ที่ 31 พ.ค. ห้าม join week_start ตรง ๆ แล้วทำข้อมูลหาย ต้องมี mapping ที่ตรวจสอบได้และรักษาวันต้นทางไว้
- ระบุว่าเดือนของยอดรายสัปดาห์จัดตามวันเริ่มสัปดาห์ ไม่ใช่ยอดรายวันของเดือนปฏิทิน และอย่ากระจายยอดเป็นรายวันโดยสมมติเอง
- SQL ในเอกสารเป็นอ้างอิง ต้องตรวจให้ครบช่วงปี เดือน ประเด็น หมวด และกลุ่มประเทศทุก query ห้ามคัดลอกตัวอย่างที่ยังไม่ครอบคลุม state แล้วทำให้ตารางกับกราฟใช้คนละขอบเขต
- สร้าง `scripts/build_db.py` และ `scripts/expected_values.py` พร้อมคำสั่งใช้งานและข้อความผิดพลาดที่บอกชื่อไฟล์/คอลัมน์ที่ขาด

## 6. กติกาข่าวเกี่ยวกับ AI และประเด็นร่วม

### ข่าว AFNC เกี่ยวกับ AI

- เริ่มจาก `item_type='Verdict'` และ `verdict_en IN ('Fake','Distorted')`
- ลบ HTML และ URL ก่อนค้นใน title + content ใช้เกณฑ์เอกสาร 02 ห้ามใช้ substring `ai` แบบหลวมที่จับ Thailand, AIS, เอไอเอส หรือ said
- แยก `mention` กับ `media_evidence` ตามกฎที่บันทึกไว้ ไม่เรียกทั้งหมดว่า “ข่าวที่ AI สร้าง”
- เก็บ matched_terms, evidence_snippet, rule/version และ review_status ให้ตรวจสอบกลับได้ ระดับ media_evidence เป็นคำบ่งชี้ ไม่ใช่คำยืนยัน
- ผู้พัฒนาต้องไม่อ้างว่าตรวจเนื้อหาครบเพียงเพราะเอกสารเดิมเขียนไว้ ให้รายงานการตรวจที่ทำจริง และคง “ต้องตรวจสอบ” เมื่อยังไม่ยืนยันจากเนื้อหา
- คำนวณรายการที่เข้ากฎใน pipeline แล้วให้แอปใช้ผลเดียวกัน ไม่สร้างกฎอีกชุดใน callback
- `impersonation_flag` เป็นป้ายวิธีการหลอก แยกจาก `category_th` ซึ่งเป็นหมวดข่าว

### ประเด็นร่วม EUvsDisinfo กับ AFNC

- ใช้พจนานุกรม 7 ประเด็นในเอกสาร 02 พร้อมกฎและคำที่ตรง ได้แก่ โควิด ยูเครน ความขัดแย้งอื่น สุขภาพ การเงิน การเมือง และสมคบคิด
- อย่าถือว่า “สงคราม” ทุกเรื่องคือ “ยูเครน”
- ประเด็นสุขภาพ การเงิน และการเมือง ใช้วิธีจัดกลุ่มสองฝั่งต่างกัน ต้องมีป้าย “วิธีจัดกลุ่มต่างกัน” และคำอธิบายที่อ่านได้จริง
- สัดส่วน = จำนวนเรื่องไม่ซ้ำในประเด็น ÷ จำนวนเรื่องทั้งหมดของแหล่งเดียวกันและช่วงเวลาเดียวกัน × 100 ห้ามใช้เฉพาะเรื่องที่จับประเด็นได้เป็นตัวหาร
- การเลือกประเด็นต้องไม่เปลี่ยนตัวหารเป็นเฉพาะประเด็นนั้นจนทุกค่าเป็น 100%
- หนึ่งเรื่องมีหลายประเด็นได้ ระบุว่าผลรวมสัดส่วนอาจเกิน 100% และนับ distinct เมื่อผ่านตารางหลายต่อหลาย

## 7. หน้าตาและโครงสร้างตามภาพ

- หน้าเปิดให้เด่นด้วย “Adidur” และคำ “จริง / หรือ / เฟค” เรียงตามภาพ พร้อมคำอธิบาย ปุ่ม “สำรวจ Dashboard” ผู้จัดทำ และรายวิชา
- ใช้ `[ชื่อผู้จัดทำ]` ที่แก้ไขได้จนกว่าจะทราบชื่อจริง
- มี 4 แท็บ: (1) AI และภัยออนไลน์ในไทย (2) ประเด็นข้อมูลบิดเบือนต่างประเทศกับไทย (3) เสรีภาพอินเทอร์เน็ต (4) แหล่งข้อมูลและดาวน์โหลด
- แท็บที่เลือกต้องเด่น ลำดับเนื้อหาต้องเห็นคำถาม ตัวกรอง KPI กราฟ ตารางหลักฐาน และข้อจำกัดได้ชัดเจน
- รักษาภาพร่างการ์ดข่าว: อันดับ 1 ใหญ่ซ้าย อันดับ 2–3 เล็กขวาบน และการ์ดยอดเข้าชมต่ำสุดขวาล่าง; มือถือเรียงตามเอกสาร 01
- ด้านล่างมี “ทำไมจึงจัดทำ Dashboard นี้” และ “ค่าแต่ละค่าคืออะไร” อธิบาย Deepfake, Misinformation, ข่าวปลอม, ข่าวบิดเบือน, การหักล้าง, คะแนน และปีข้อมูล/ปีรายงาน
- ใช้โทน afmhot/gist_heat: ครีม ดำ แดง ส้ม เหลือง ตาม tokens ในเอกสาร 01 ไม่ใช้พื้นชมพูในสเก็ตช์เป็นสีจริงโดยอัตโนมัติ
- สเกลปริมาณใช้ค่ามาก = เข้มเหมือนกันทั้งเว็บ ตามเอกสาร 01 พร้อม legend ที่มีตัวเลข; heatmap สองแหล่งใช้สเกลเดียวกัน 0–100% ช่องไม่มีข้อมูลต้องต่างจากค่า 0
- สถานะข่าวจริง/ปลอม/บิดเบือนใช้สี ลาย และป้ายข้อความคงที่ ไม่ใช้สีอย่างเดียว
- ฟอนต์ Noto Sans Thai สำหรับหัวเรื่อง Sarabun สำหรับเนื้อหา และตัวเลขที่จัดหลักตรงกัน รักษาสระวรรณยุกต์ไทยไม่ถูกตัด
- รองรับโหมดสว่าง/มืดตามระบบ พร้อมอัปเดตสีแกน ตัวอักษร legend และ tooltip ของ Plotly

- ทดสอบ 360px, 768px และ 1280px ไม่มีการล้นแนวนอนทั้งหน้า ตารางเลื่อนภายในกรอบได้ แท็บมือถือเลื่อนได้

## 8. ความสามารถของ Dashboard แต่ละแท็บ

### แท็บ 1 — AI และภัยออนไลน์ในไทย

ทำ K1.1–K1.4, C1.1–C1.6 และ T1 ให้ครบ:

- KPI แยกเหตุการณ์ Deepfake, ข่าวเกี่ยวกับ AI, คดี ACSC, ความเสียหาย และบาทต่อคดี ทุกใบมีหน่วย แหล่ง และช่วงเวลา
- กราฟเส้น AIID กับ AFNC เป็นสองแผงบนแกนเวลาเดียวกัน ไม่รวมหน่วยต่างชนิดไว้เป็นยอดเดียว
- ข่าว AFNC แยกเส้นระดับ mention กับ media_evidence และกราฟแท่งหมวด พร้อมป้ายแอบอ้างแยกต่างหาก
- การ์ดข่าวอันดับ 1–3 และต่ำสุดคำนวณจาก `view_count` ภายในตัวกรองปัจจุบัน กรณีคะแนนเท่ากันใช้กติกาที่แน่นอน เช่น post_id
- ระบุ “ยอดเข้าชม ณ วันที่เก็บข้อมูล” ตาม metadata ไม่ใช้วันที่ปัจจุบันแทน และบอกว่ายอดเข้าชมไม่ใช่ความน่าเชื่อถือหรือความรุนแรง
- เมื่อข่าวมีไม่ครบ 4 รายการ แสดงจำนวนจริงและช่องว่างพร้อมเหตุผล ห้ามทำข่าวซ้ำเพื่อให้ครบ layout
- ACSC มีกราฟแท่งคดีและกราฟเส้นความเสียหายแยกแผง ช่องว่างเมื่อไม่รายงาน จุดปัดเลขและ suspect มีเครื่องหมาย พร้อมรายละเอียดและลิงก์เมื่อแตะสัปดาห์
- บาทต่อคดี = ผลรวมความเสียหาย ÷ ผลรวมคดี เฉพาะแถวที่มีทั้งคู่และตัวหารไม่เป็นศูนย์ ไม่เฉลี่ยค่าเฉลี่ยรายสัปดาห์
- ตารางหลักฐานมีวันที่ หัวข้อ แหล่ง หมวด กฎ/คำที่ตรง ข้อความหลักฐาน สถานะตรวจ และลิงก์ต้นทาง
- ตัวกรองหมวด ระดับ AI และการแอบอ้างมีผลเฉพาะ AFNC ไม่กรอง AIID หรือ ACSC ห้ามติดป้ายคดี ACSC ว่าเป็นคดีจาก AI

### แท็บ 2 — ประเด็นข้อมูลบิดเบือนต่างประเทศกับไทย

ทำ K2, C2.1–C2.5 และ T2 ให้ครบ:

- Heatmap EUvsDisinfo กับ AFNC แยกสองแผง ปี × ประเด็น แสดงจำนวน ตัวหาร และสัดส่วนเมื่อแตะ
- กราฟเส้นสัดส่วนประเด็นที่เลือก กราฟแท่งซ้อนหมวด AFNC และแผงบริบท AIID Misinformation
- ค่าเริ่มต้น **ค.ศ. 2020–2022 / พ.ศ. 2563–2565** ตามการปรับในเอกสาร 01–02 ไม่ใช้ปี 2019 เป็นปีเต็ม
- ปี 2019 ของ AFNC มีป้ายไม่เต็มปี ปี 2023 ของ EU มีถึง 1 ส.ค. ตาม snapshot ที่ตรวจจริง ปีหลังจากนั้นฝั่ง EU เป็นไม่มีข้อมูล ไม่ใช่ศูนย์
- ตารางวางหลักฐานในประเด็นเดียวกันของสองแหล่งคู่กัน พร้อมป้ายว่าไม่ได้จับคู่เป็นข่าวเดียวกัน
- ห้ามเรียก EUvsDisinfo ว่าฐานข่าวปลอมทั้งหมดทั่วโลก และห้ามสรุปว่าประเด็น “ข้ามมาไทย” จากกราฟนี้

### แท็บ 3 — เสรีภาพอินเทอร์เน็ต

ทำ K3, C3.1–C3.4; C3.5 แผนที่เป็นส่วนเสริม:

- KPI ไทยแสดงคะแนน สถานะ data_year และ report_edition ตามปีที่เลือก หากแสดงประเทศที่เลือกเพิ่มต้องมีชื่อกำกับชัด ไม่เปลี่ยนค่าภายใต้ป้าย “ไทย”
- แท่งแนวนอนเปรียบเทียบประเทศในปีเดียว ค่าเริ่มต้นอาเซียนที่มีข้อมูลในไฟล์ ใช้ iso3 ระบุประเทศและเน้นไทย
- อันดับคำนวณจากประเทศไม่ซ้ำในกลุ่มและปีเดียว ระบุจำนวนประเทศ กลุ่ม และกติกาคะแนนเสมอ ไม่รวมหลายปีและไม่ให้การ join หลายกลุ่มเพิ่มจำนวนประเทศ
- แท่งซ้อนองค์ประกอบคะแนน 25/35/40 และ drill ประเทศ → ปี → องค์ประกอบ โดยไม่สร้างข้อมูลรายเดือน
- เส้นสองแผงช่วง 2019–2024 แสดงคะแนนไทยและจำนวน **คำตัดสิน Verdict ทั้งหมดของ AFNC** ให้ชื่อตัวชี้วัดตรงสูตร ไม่เรียกเป็นจำนวนข่าวปลอมทั้งหมด
- กราฟคู่นี้ต้องมีข้อความ “ไทยเท่านั้น · แสดงคู่กันเพื่อเป็นบริบท ไม่ได้วัดความสัมพันธ์”
- ตัวกรองประเทศเปลี่ยนเฉพาะ FOTN ไม่ย้ายข่าว AFNC ไปเป็นของประเทศที่เลือก และไม่ผูกแผงบริบท EU เข้าประเทศโดยไม่มีข้อมูล

### แท็บ 4 — แหล่งข้อมูลและดาวน์โหลด

ทำ S4.1–S4.3 และ D4.1–D4.3 ให้ครบ:

- อธิบายชุด AIID, FOTN, EUvsDisinfo, AFNC, ACSC และ weekly_panel: ผู้จัดทำ ความหมายหนึ่งแถว ช่วงเวลา วันไฟล์ จำนวนก่อน/หลัง คอลัมน์ สูตร ข้อจำกัด และลิงก์
- แสดงพจนานุกรมข้อมูล สูตร KPI กฎข่าว AI และพจนานุกรมประเด็น โดยระบุกฎที่โครงการกำหนดเอง
- ปุ่ม 3 กลุ่มแยกชัด: ต้นฉบับ / ข้อมูลที่เตรียมแล้ว / ผลตามตัวกรองปัจจุบัน
- ข้อมูลที่สร้างใหม่ส่งเป็น CSV UTF-8 พร้อม BOM เปิดภาษาไทยได้ พร้อมชื่อไฟล์ระบุแท็บและตัวกรอง
- การดาวน์โหลดต้องใช้ query และ state เดียวกับผลที่ผู้ใช้เห็น ดาวน์โหลดครบชุดที่กรองไม่ใช่เฉพาะหน้าตารางที่แสดง พร้อมบอกขอบเขต
- ดาวน์โหลดผลของแท็บ 1–3 ได้ทั้งที่แท็บนั้นและจากแท็บ 4 โดยไม่สูญเสีย state
- ปุ่มต้นฉบับส่งไฟล์ต้นฉบับเดิม ไม่แทนด้วยข้อมูลแปลงแล้ว

## 9. State, Filter, Drill down/up และ URL

- ใช้ state แยกแต่ละแท็บตามเอกสาร 01 มีส่วนกลางที่ทุก KPI กราฟ ตาราง การ์ด สรุป และ export ใช้ร่วมกัน
- ให้ callback รับการคลิก/แตะและตัวกรองเข้ามาอัปเดต state แล้ว render ผลอย่างสอดคล้องตามเอกสาร 04 ระวัง callback วนและ duplicate output
- กราฟต้องเชื่อมเฉพาะมิติที่ใช้ร่วมกันได้จริง กราฟที่ไม่รับตัวกรองนั้นคงค่าภายใต้ขอบเขตของตัวเองพร้อมป้ายบอก ไม่มีการเปลี่ยนเป็นศูนย์ปลอม
- AIID/AFNC: ปี → เดือน → รายการ; ACSC: เดือน → สัปดาห์ → รายละเอียดต้นทาง; FOTN: ประเทศ → ปี → องค์ประกอบ
- ทุกเส้นทางมี breadcrumb ย้อนระดับ และล้างตัวกรองได้ การย้อนระดับลบเฉพาะรายละเอียดระดับล่าง ไม่ล้างตัวกรองอื่นโดยไม่ตั้งใจ
- การเปลี่ยนแท็บรักษา state ของแต่ละแท็บ ลิงก์ URL เปิดซ้ำแล้วคืนตัวกรองเดิม ใช้ Back/Forward ได้ และตรวจค่าพารามิเตอร์ที่ผิดรูปแบบ
- การคลิก legend ถ้าใช้เป็นตัวกรองต้องอัปเดต state และผลที่เกี่ยวข้องจริง ไม่ใช่เพียงซ่อนเส้นแต่ KPI และ export ยังนับรวม
- ใช้งานบนจอสัมผัสได้ครบ แสดงค่าจุดที่แตะในแผงรายละเอียด ไม่พึ่ง hover อย่างเดียว และมีวิธีเลือกค่าผ่านตัวกรองเมื่อใช้คีย์บอร์ด
- ข้อมูลว่างต้องแยก “ไม่มีรายการตรงตัวกรอง”, “แหล่งนี้ไม่มีข้อมูลช่วงนี้” และ “ไม่รวมเพราะ suspect”
- แสดงปี พ.ศ. ในส่วนติดต่อผู้ใช้ แกน ตาราง breadcrumb และชื่อไฟล์ แต่เก็บปีในฐานข้อมูลและ URL เป็น ค.ศ. ตามกฎเดียวกัน

## 10. โครงสร้างโครงการและการรัน

ปรับตามโครงสร้างจริง โดยแยกความรับผิดชอบอย่างน้อย:

```text
Datasets/                         # รักษาไฟล์ต้นฉบับทั้ง 4 ไฟล์
app/
  app.py                          # Dash app และเส้นทางหน้า
  state.py                        # ค่าเริ่มต้น state, URL, ปี
  queries.py                      # SQL ที่ใช้ร่วมกันและ bind parameters
  figures.py                      # Plotly และ theme
  pages/                          # หน้าเปิด + 4 แท็บ
  components/                     # filters, KPI, news, breadcrumb, evidence
  assets/                         # CSS, theme script และ font ถ้ามี
scripts/
  build_db.py
  expected_values.py
data/
  adidur.db                       # สร้างซ้ำได้ ไม่ใช่ข้อมูลสมมติ
  processed/                     # export ที่เตรียมแล้ว
  manifest.json
docs/
  BRD.md
  REQUIREMENTS_TRACEABILITY.md
  DATA_PREPARATION.md
  DECISIONS.md
  TEST_REPORT.md
tests/
README.md
requirements.txt                  # เวอร์ชันที่ใช้ทดสอบจริง
.gitignore
```

เพิ่มไฟล์ configuration สำหรับรันหรือ deploy เท่าที่จำเป็น ระบุคำสั่งติดตั้ง เตรียมข้อมูล ตรวจค่า ทดสอบ และเปิดเว็บให้ครบ ตัวอย่างที่ต้องทำให้สอดคล้องกับโค้ดจริง:

```bash
python -m pip install -r requirements.txt
python scripts/build_db.py --input Datasets --output data/adidur.db
python scripts/expected_values.py data/adidur.db
python -m pytest -q
python -m app.app
```

อย่านำ CLI ตัวอย่างไปใส่ README ถ้าโค้ดยังไม่รองรับจริง

- ประมวลผล Excel/CSV ล่วงหน้า ไม่อ่านใหม่ทุกครั้งที่กด filter
- เก็บ state ใน browser เฉพาะค่าตัวกรองและข้อมูลจำเป็น ไม่ส่งเนื้อหาข่าวทั้งฐานเข้า dcc.Store
- ใช้ pagination/โหลดรายละเอียดตามต้องการ SQL แบบ bind parameters และ allowlist ชื่อตารางสำหรับ export
- วัดเวลาเตรียมข้อมูล เปิดหน้า และอัปเดตตัวกรองในสภาพแวดล้อมที่ทดสอบจริง ระบุเป้าหมายใน BRD และผลที่วัดได้ ไม่แต่งตัวเลขประสิทธิภาพ
- **Dash ต้องมี Python server** ให้จัดวิธีรันบนบริการที่รองรับ Python หนึ่งวิธี และตรวจคู่มือปัจจุบันของบริการนั้น ห้ามเขียนว่าเผยแพร่ Dash ตรงบน GitHub Pages ได้
- ถ้า repository เปลี่ยนจนมีข้อกำหนด Static/GitHub Pages ชัดเจน ต้องบันทึกความขัดแย้งทางสถาปัตยกรรมและทางเลือกก่อนเปลี่ยน stack ไม่เปลี่ยนเองโดยไม่อธิบาย
- การเตรียมไฟล์ deploy ไม่เท่ากับเผยแพร่สำเร็จ รายงานสถานะให้ตรง

### 11.2 กติกาและความสอดคล้อง

- ตรวจว่าผลรวมและรายการของ KPI กราฟ ตาราง การ์ด สรุป และ export ตรงกันภายใต้ตัวกรองเดียวกัน
- เปลี่ยนหมวด/ระดับ AI/แอบอ้างแล้ว ACSC และ AIID ไม่ถูกกรองผิด
- เปลี่ยนประเทศแล้ว AFNC ยังเป็นข้อมูลไทย และไม่เปลี่ยนตามประเทศ
- ACSC ในช่วงอ้างอิงเดิมมี 51 ช่องสัปดาห์ 48 ช่องมีข้อมูลและ 3 ช่องว่างเมื่อรวม suspect; แยกการตัด suspect ออกจากสัปดาห์ที่ไม่รายงาน
- สัปดาห์ 8 วันไม่หายจากการเชื่อม panel และยอดรวมตารางกับกราฟยังตรงกัน
- ตรวจ 0 กับ NULL, ตัวหารศูนย์, เลือกช่วงไม่มีข้อมูล, ตัด suspect, เลือกปีไม่เต็ม และช่วงนอก coverage
- ตรวจ heatmap ตัวหารไม่เปลี่ยนตามการเลือกประเด็น และไม่มีการนับซ้ำจาก keywords/themes
- ตรวจ ranking ประเทศไม่ซ้ำในปีเดียว และผลรวมองค์ประกอบคะแนนตรง total_score
- ตรวจข่าว 0, 1, 2, 3 รายการและยอดเข้าชมเสมอกัน โดยไม่ทำข่าวซ้ำในการ์ด
- ตรวจ CSV ขึ้นต้น `EF BB BF`, ชื่อคอลัมน์ไทยอ่านได้ และ export ครบรายการตาม state
- ตรวจ state → URL → state, reload, Back/Forward, ข้ามแท็บ, reset และ drill up ทุกระดับ
- ทดสอบกฎ AI ว่าไม่จับ Thailand/AIS/เอไอเอส/said และรักษาข้อความหลักฐาน

### 11.3 เปิดเว็บและตรวจหน้าจอ

- เปิดแอปจริง ทดสอบทุกแท็บ ตัวกรองทุกชนิด คลิกกราฟ drill down/up ล้างตัวกรอง ดาวน์โหลด และลิงก์ต้นทางที่สุ่มตรวจ
- ใช้ browser test เช่น Playwright เมื่อสภาพแวดล้อมรองรับ พร้อมบันทึก console errors และปัญหา callback
- ตรวจ 360/768/1280px ทั้งโหมดสว่างและมืด อย่างน้อยหน้าเปิดและแท็บ 1; ตรวจแท็บที่เหลือว่ากราฟและตารางไม่ล้นหรือถูกตัด
- บันทึกภาพหน้าจอเพื่อใช้เป็นหลักฐานการตรวจ UI พร้อมขนาดและโหมดจริง
- ระบุข้อจำกัดของการจำลอง touch และอย่าเรียกว่าผ่านบน iPad จริงถ้าทดสอบแค่ viewport
- ถ้า browser หรือเครือข่ายใช้ไม่ได้ ให้รายงาน “ยังไม่ได้ทดสอบ” แยกจาก “ผ่าน” และ “ไม่ผ่าน” ไม่สร้างหลักฐานแทน

ใน `docs/TEST_REPORT.md` ให้มี test case, expected, actual, status, คำสั่งที่รัน, วันที่, environment และหลักฐานที่มี พร้อมรายการที่ยังค้างและผลต่อการใช้งาน

## 12. ลำดับการทำงานและสิ่งส่งมอบ

ทำตามลำดับนี้โดยไม่จบงานกลางทางหลังส่งแผน:

1. ตรวจ repository/branch/ไฟล์/เอกสาร แล้วสรุปโครงสร้างจริงและข้อขัดแย้งสั้น ๆ
2. สร้าง BRD และ traceability ที่ผูกกับรหัสในเอกสาร 01
3. ตรวจคุณภาพข้อมูล ทำ pipeline ฐานข้อมูล manifest และตรวจค่าคาดหวัง
4. ทำหน้าเปิดกับระบบดีไซน์ตามภาพ ต่อทุกแท็บกับข้อมูลจริง
5. ทำ filter, drill, reset, URL, ตารางหลักฐาน สรุป และ download ให้ครบ
6. รันการทดสอบ เปิดเว็บ ตรวจ UI แก้ข้อผิดพลาด และปรับเอกสารให้ตรงผลงาน
7. ส่งมอบซอร์สโค้ด ไฟล์ข้อมูลที่เตรียมแล้ว สคริปต์รันซ้ำ BRD, traceability, README, วิธี deploy และผลทดสอบจริง

หากขาดไฟล์จำเป็น ให้แจ้งชื่อและผลกระทบเฉพาะจุด ทำส่วนที่ไม่ต้องใช้ไฟล์นั้นต่อ ห้ามสร้างข้อมูลปลอมแทน และห้ามอ้างว่าทดสอบผ่านส่วนที่ไม่มีข้อมูล

คำตอบสุดท้ายให้รายงาน:

- ทำอะไรเสร็จและผู้ใช้ใช้งานอะไรได้แล้ว
- branch/commit ที่ทำงาน และได้ push/deploy หรือยัง
- ลิงก์/เส้นทาง BRD, traceability, README, รายงานทดสอบ และไฟล์ส่งมอบ
- คำสั่งเปิดเว็บที่ทดสอบจริง
- สรุปข้อค้นพบที่คำนวณแล้ว พร้อมข้อจำกัด ไม่ยกสมมติฐานมาเป็นผลการศึกษา
- สิ่งที่ผ่าน ไม่ผ่าน ยังไม่ได้ทดสอบ และงานที่ยังค้างตามจริง

**Definition of Done:** เว็บไซต์เชื่อมข้อมูลจริงครบทุกแท็บ ทุกองค์ประกอบที่ระบุทำงานตาม BRD และภาพอ้างอิง เปิดหลักฐานและดาวน์โหลดได้ เตรียมข้อมูลซ้ำได้ มีหลักฐานการทดสอบตามขอบเขตที่ทำจริง และไม่มีข้อความสรุปเกินข้อมูล
